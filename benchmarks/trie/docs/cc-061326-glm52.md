# CC 061326 / GLM-5.2: causal replay and zero-output removal

This opt-in conversion builds on the existing `cc_weka` adapter. It changes
benchmark data and event dependencies only. It does not modify engine,
cache, or routing implementations. The default converter behavior remains
`recorded-think` timing and raising zero output to one token.

## Prepare

From `benchmarks/trie`, with the normal Trie dependencies installed (`uv sync`):

```bash
uv run python scripts/convert_traces_to_strict.py cc_weka \
  --input /path/to/cc-061326/traces.jsonl \
  --target-tokenizer /path/to/GLM-5.2-NVFP4 \
  --cc-timing causal-gaps --cc-zero-output drop-advance \
  --output cc-061326-glm52.workload.jsonl --workers 4

uv run python scripts/convert_traces_to_strict.py validate \
  --workload cc-061326-glm52.workload.jsonl \
  --tokenizer /path/to/GLM-5.2-NVFP4 \
  --source /path/to/cc-061326/traces.jsonl --workers 4 \
  --report cc-061326-glm52.validation.json
```

The source is never edited. The compact workload carries block runs, the exact
target vocabulary pool, request lengths and source identities. Token blocks
are materialized by the existing client before each request, preserving
same-session prefix sharing across parent/subagents. Existing replay-cycle
content isolation is unchanged; this does not add cross-session cache reuse.

## Timing and dependencies

The existing prefix/time chain partition and inferred parent/join choices are
retained. The trace does **not** record authoritative parent request or join
IDs; these are reconstructed dependencies, not recovered original Claude
control flow.

For each model call, the new policy takes the latest of its preceding
same-chain completion and required child completions. It waits only the
remaining gap to the call's recorded start. Child launch is anchored to the
latest parent call started by that time: completion if it had finished,
otherwise client event start plus the recorded offset. For example, parent
starts at 100s, child starts at 100.5s while the parent is still running:
child waits 0.5s after parent event start. `when: start` means **client event
processing starts**, before prompt preparation, not GPU admission or an HTTP
acknowledgement. Omitted `when` still means completion.

This avoids counting old child model execution time again as an external
wait, and avoids using a stale first-child `think_time` as a second launch
delay. Raw think/start values are retained in the task's policy receipt.
Every task is simulated with its recorded API durations before deletion; its
model-call starts must match the source timeline within 5ms. This verifies the
reconstruction's timing arithmetic, not the truth of inferred causality or
runtime wall-clock precision.

## Delete zero output and advance the successor

Chains are detected **before** deletion. Each zero-output model call is
replaced with a zero-duration control milestone that sends no HTTP request.
The next surviving call in that same chain skips its own preceding wait, so
it takes the earlier call's scheduling slot. Its original prompt, output
length, source ID and timestamp stay unchanged. Already-required joins still
apply: advancing a call never allows it to bypass a child result it needs.

Consecutive zeros retain only the first slot's wait. Trailing zeros also lose
their preceding waits. Their control milestones keep existing spawn/join
references valid; an entirely empty child chain becomes `control_only`.
No new model requests are invented. A wholly empty task is rejected by the
normal parser (none occurs in 061326).

`metadata.cc_replay_policy` records every deletion, its same-chain successor
if any, original timestamps and the effective start in the simulated modified
timeline. These effective starts are not prescribed wall-clock deadlines:
real model/queue durations propagate through dependencies.

Use `warm_start=off`: a stationary cut using the original timestamps is not
valid after this rewrite, and the client rejects it for `drop-advance`.

## Replay configuration

Example workload options to add to the usual endpoint/model/run settings:

```bash
uv run trie workload_path=cc-061326-glm52.workload.jsonl \
  endpoint=http://ROUTER/v1 model=MODEL \
  strict_replay=true replay_output_mode=model max_retries=0 stream=true \
  lazy_workload=true warm_start=off delay_scale=1 \
  concurrency=224 duration=5400 timeout=3600 cache_salt_mode=session
```

Concurrency counts **whole root tasks**, with their subagents running according
to the DAG. There are 183 distinct source tasks, so concurrency 224 repeats
some templates with the existing isolated replay-cycle content. The task-wide
cache salt allows sharing within each invocation. Do not copy another
experiment's synthetic DSPARK acceptance setting: `replay_output_mode=model`
uses the model's actual output; it does not force invented output IDs. This
example describes client options, not an authorized launch or performance
measurement.

The full workload requires a context limit above 256K: the longest retained
input + output is 996,579 tokens. The local GLM configuration declares
1,048,576 positions. Engine context/admission capacity and EAGLE/PD operation
at that length still require a GPU check; this CPU conversion is not that
check. No prompt/output length was clipped to fit 256K.

The synthetic inputs reproduce block identity and lengths, not Claude text,
semantic quality or the original model's MoE expert distribution. Actual
model outputs also need not match the next recorded synthetic input. These
limits apply to cache/performance interpretation.
